# 主动删除记忆的启动数量监测修复

## 问题
旧逻辑把下次启动的总数/私聊数与上次快照比较，主动删除后没有扣减基线，导致正常操作产生 Memory/StartupCountDrop 红色日志。

## 修改
- 单条删除、批量删除、按来源删除和清空当前印象统一核对删除前匹配 ID 与删除后仍存在 ID，仅扣减确实消失的目标项数量与私聊来源数量。
- 更新基线采用原基线减去已验证删除数，不直接改成当前总数，保留对其他未解释减少的检测。
- finally 记录部分失败时实际完成的数量；删除与核对在不可取消区间中完成，避免退出页面时已删除但未记账。
- 启动快照、保留期清理计数和主动删除使用同一互斥锁，避免本进程这些路径覆盖彼此基线。
- 日志 Memory/UserDeletion 仅含原因和数量，不含记忆正文；清理前后变化记录为普通 Memory/CleanupCountChange，不再统一标成启动异常。
- 未解释的启动减少仍保留 StartupCountDrop。历史红色日志保留，无法追溯证明其对应主动删除，未批量抹除。

## 验证
:app:testDebugUnitTest 成功，346 项测试全部通过。新增 6 项覆盖私聊删除、其他来源删除、未解释减少保留、无操作与部分删除计数、下限、损坏或缺失基线解析。此次没有运行 UI 自动化删除测试。

## 范围
修复以上用户手动记忆删除入口和启动/保留期计数日志；不宣称已为所有数据库清理、恢复、角色删除与其他后台操作建立完整删除审计。数量监测本身不能检测被同期新增抵消的丢失。
